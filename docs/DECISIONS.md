# CartCart Decisions

Status: Initial public decision log
Last updated: 2026-06-02

## Purpose

This file records accepted and pending product/architecture decisions that affect implementation. Pending decisions may have a current recommendation, but should be confirmed before dependent implementation work begins.

Status meanings:

- `accepted`: Use this direction unless new evidence or a project-owner decision changes it.
- `pending`: Recommended direction exists, but implementation should not treat it as final until the relevant task confirms it.

## Decision Table

| Decision | Status | Recommendation | Rationale | What Would Change It |
| --- | --- | --- | --- | --- |
| Default region | `pending` | Make region visible and editable from the first session. If the user provides no region, use a configured local-development default, initially `US`, and mark it as inferred/defaulted rather than user-confirmed. | Search, availability, warranty, shipping, currency, and seller trust are region-dependent. The plan requires region to be visible, editable, and used in source selection, but it does not yet finalize a launch/default region. | Project owner selects a different launch region, the UI requires explicit region before running, or locale/browser-based inference is approved with privacy constraints. |
| First search provider | `pending` | Implement Tavily first if an API key and terms are acceptable; otherwise implement Brave Search first. Keep the provider behind an adapter interface. | Tavily is recommended because search and extraction both matter for agent workflows. Brave is a credible independent-index alternative. The app should not hard-wire one provider. | Tavily key is unavailable, cost/terms are unacceptable, Brave coverage is materially better for shopping queries, or another provider is approved before provider implementation starts. |
| Optional SerpApi use | `accepted` | Keep SerpApi optional and adapter-based. Do not make it a core MVP dependency. | Structured shopping results may be useful, but SerpApi adds cost, dependency, and legal/business risk. CartCart should still work through general search and extraction paths. | The project owner explicitly accepts SerpApi cost/terms and wants shopping-specific structured results in MVP, or provider tests show general search cannot produce adequate shopping candidates. |
| Broad generic agent strategy | `accepted` | Keep `GenericProductAnalystAgent` as the buy-anything fallback for every normal shopping category. Add specializations as refinements rather than blocking unsupported categories. | CartCart should start broad and become deeper over time. A reliable generic agent prevents category dead ends and gives future specialists a safe fallback. | A category becomes legally or operationally unsafe to handle generically, or evals show generic output is misleading for a specific category and must be blocked or constrained. |
| MVP technology domain and specialists | `accepted` | Include `TechnologyDomainAnalystAgent` in MVP, with MVP specialists for monitors, smartphones, laptops, earphones/headphones, TVs, and smartwatches. Route technology products through the domain layer before specialist selection. | Adding the higher-level technology domain early is easier than retrofitting it after several direct specialists exist. The domain layer can own shared technology-product reasoning while specific specialists refine category details. | MVP scope must be reduced for delivery reasons, or evals show a specialist is too weak to ship and should fall back to technology-domain analysis until improved. |
| Reusable source-agent ownership | `accepted` | Keep reusable source intelligence agents outside the product/category hierarchy. They gather source-specific evidence and hand structured evidence back to product analysts and decision agents; they do not make final purchase recommendations. | YouTube reviews, Reddit community discussion, Amazon product/listing/review evidence, IKEA regional official-store evidence, marketplace product intelligence, brand stores, professional reviews, and community signals can support multiple product categories. Treating them as reusable tools avoids duplicating source logic inside every specialist. | A future source capability becomes category-specific enough that it belongs inside a specialist, or a provider/compliance constraint requires narrower ownership. |
| Reusable source intelligence scope | `accepted` | Source intelligence agents must retrieve usable source-backed information, not only availability. Depending on the source, they may gather product descriptions/specs, review signals, owner complaints, seller/fulfillment signals, price/currency, regional availability, shipping/store context, warranty/return context, and explicit evidence gaps. | Availability alone is too narrow for decision support. CartCart needs source evidence that downstream analysts can cite, discount, compare, or use to surface warnings. | Provider terms or source access restrict a specific field, in which case the source agent should return a capability flag or evidence gap rather than faking the field. |
| Required MVP reusable source agents | `accepted` | Treat `YouTubeReviewIntelligenceAgent`, `RedditCommunityIntelligenceAgent`, `AmazonProductIntelligenceAgent`, and `IKEAStoreIntelligenceAgent` as `required-mvp` reusable source intelligence agents. Keep fixture/stub mode working while live provider access is configured explicitly. | These sources cover complementary evidence: video reviews, community owner signals, global marketplace/listing/review information, and region-specific official IKEA availability/product information. They are useful across categories and should be implemented as reusable tools rather than category-specific logic. | MVP scope is explicitly reduced by the project owner, provider access proves infeasible after due diligence, or a source must be postponed for legal/compliance reasons. |
| YouTube review intelligence MVP status | `accepted` | Promote `YouTubeReviewIntelligenceAgent` to `required-mvp`. Implement it after the generic workflow and provider abstractions exist, with metadata-only and unavailable-transcript fallbacks. | Video reviews can add high-value real-world evidence across many categories. The source is now part of the required reusable source intelligence set, but transcript access still must be represented honestly. | Provider constraints make even metadata discovery infeasible, or the project owner explicitly reduces source-intelligence MVP scope. |
| YouTube transcript/provider strategy | `accepted` | Use official YouTube Data API metadata where configured. Do not assume transcript access. Use transcript text only through authorized official caption access, user-provided transcript input if later added, or an explicitly approved third-party transcript provider. Always represent transcript gaps. | Official metadata discovery is feasible, but official caption download is authorization-scoped and not a general public transcript API. Unofficial transcript providers carry reliability, quota, terms, and compliance risk. | A compliant transcript provider is approved, the project owner accepts a specific third-party provider risk, or the MVP deliberately chooses metadata-only video evidence. |
| Reddit community intelligence strategy | `accepted` | Implement Reddit community intelligence through approved domain-scoped search and compliant extraction of public `reddit.com` content, with source links, recency/context where available, and quality warnings. Treat Reddit as qualitative community signal unless corroborated. | Reddit can surface owner complaints, durability issues, setup pain, and support experiences that retailer pages omit, but comments are anecdotal and can be biased, stale, incomplete, or manipulated. | Reddit source access becomes noncompliant or too brittle, a better approved community-data provider is selected, or evals show community signals add more noise than value for MVP. |
| Amazon product intelligence strategy | `accepted` | Implement Amazon product intelligence as a reusable source agent that retrieves product/listing identity, marketplace/region context, seller/fulfillment signals, ship-to-region or availability evidence, product-page information, and review signals when compliant access is available. Preserve neutral links and no affiliate logic. | Amazon can ship across many regions and has broad product/review coverage, but marketplace seller risk, variant ambiguity, review quality, regional availability, and provider terms must be handled explicitly. | Approved Amazon access is unavailable, a third-party provider is accepted instead, or the project owner narrows MVP marketplace support. |
| IKEA regional store intelligence strategy | `accepted` | Implement IKEA as a reusable official-store source agent that checks whether IKEA has relevant country/region presence and retrieves official product information, regional price/currency, and availability/store/delivery evidence where available. Do not infer global shipping. | IKEA has broad international store presence but not universal global shipping. Its value is region-aware official source evidence, especially for furniture and home categories, without making it a generic marketplace. | IKEA source access is unavailable or noncompliant, region coverage is too sparse for MVP, or a broader official-store provider supersedes the specific IKEA path. |
| Suspicious-listing treatment | `accepted` | Treat seller/listing legitimacy as a first-class analysis concern. Suspicious or weak listings must be surfaced, penalized, blocked, or clearly warned about separately from product quality. Deterministic suspicious flags must not be silently overridden by agent output. | CartCart exists partly to help users avoid bad or suspicious purchases. A good product from a risky seller should not become a safe recommendation. | Trust signals prove too sparse for a category/source, requiring an `unknown` trust state, or legal/product guidance changes how risk wording should be presented. |
| Raw snapshot retention | `accepted` | Store structured source and evidence records in SQLite. Store bulky raw artifacts under `data/artifacts/` only when useful for auditing, debugging, extraction replay, or evals. Use configurable local retention windows and `scripts/local/cleanup-artifacts.sh --yes` before live-provider work when cleanup is needed. | The plan favors local evidence retention for session continuity and evalability, but raw HTML, extracted text, screenshots, traces, and eval outputs can grow large and may contain sensitive content. The default policy keeps large artifacts in files, references them from SQLite where needed, disables screenshots by default, and explicitly excludes cross-session preference profiling. | Storage/privacy concerns require shorter retention, provider terms restrict stored content, or eval/debug needs require explicit longer retention for selected fixtures. |
| Observability backend choice | `pending` | Use OpenTelemetry concepts from the start and keep exporters backend-neutral. Use Logfire as the default local/development backend if acceptable; otherwise use console/local OTEL export with structured JSON logs. | Logfire aligns with Pydantic, FastAPI, AI/LLM observability, and span-based evals. Exporter-neutral instrumentation avoids locking implementation to one backend. | Logfire is not acceptable for privacy/cost/account reasons, another OTEL backend is selected, or local-only console/file traces are preferred for MVP. |
| Future domain-layer timing | `accepted` | Add `TechnologyDomainAnalystAgent` now because multiple MVP technology specialists are approved. Keep other broad domain layers, such as kitchen appliances, postponed until they have multiple specialists or shared rules. | Higher-level domain agents are harder to add after direct specialist routing spreads. Adding the technology domain now preserves modularity while avoiding empty non-technology layers. | A future non-technology domain gains enough specialists or shared evaluation rules to justify a domain layer. |
| Tool-vs-handoff policy | `accepted` | Use typed steps, tools, or sub-runs for MVP agents. Do not use OpenAI Agents SDK handoffs as the normal control plane. Consider handoffs only when a specialist must take over a conversational turn. | CartCart needs persisted workflow state, retries, source evidence, evalability, and inspectable intermediate artifacts. Deterministic orchestration keeps those responsibilities explicit. | A future conversational workflow needs specialist ownership of a user turn and can still preserve persistence, traceability, and fallback behavior. |
