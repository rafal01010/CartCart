# CartCart Decisions

Status: Initial public decision log
Last updated: 2026-05-29

## Purpose

This file records accepted and pending product/architecture decisions that affect implementation. Pending decisions may have a current recommendation, but should be confirmed before the checklist task that depends on them.

Status meanings:

- `accepted`: Use this direction unless new evidence or a project-owner decision changes it.
- `pending`: Recommended direction exists, but implementation should not treat it as final until the relevant task confirms it.

## Decision Table

| Decision | Status | Recommendation | Rationale | What Would Change It |
| --- | --- | --- | --- | --- |
| Default region | `pending` | Make region visible and editable from the first session. If the user provides no region, use a configured local-development default, initially `US`, and mark it as inferred/defaulted rather than user-confirmed. | Search, availability, warranty, shipping, currency, and seller trust are region-dependent. The plan requires region to be visible, editable, and used in source selection, but it does not yet finalize a launch/default region. | Project owner selects a different launch region, the UI requires explicit region before running, or locale/browser-based inference is approved with privacy constraints. |
| First search provider | `pending` | Implement Tavily first if an API key and terms are acceptable; otherwise implement Brave Search first. Keep the provider behind an adapter interface. | Tavily is recommended because search and extraction both matter for agent workflows. Brave is a credible independent-index alternative. The app should not hard-wire one provider. | Tavily key is unavailable, cost/terms are unacceptable, Brave coverage is materially better for shopping queries, or another provider is approved before provider implementation starts. |
| Optional SerpApi use | `accepted` | Keep SerpApi optional and adapter-based. Do not make it a core MVP dependency. | Structured shopping results may be useful, but SerpApi adds cost, dependency, and legal/business risk. CartCart should still work through general search and extraction paths. | The project owner explicitly accepts SerpApi cost/terms and wants shopping-specific structured results in MVP, or provider tests show general search cannot produce adequate shopping candidates. |
| Broad generic agent strategy | `accepted` | Keep `GenericProductAnalystAgent` as the buy-anything fallback for every normal shopping category. Add specializations as refinements rather than blocking unsupported categories. | CartCart should start broad and become deeper over time. A reliable generic agent prevents category dead ends and gives future specialists a safe fallback. | A category becomes legally or operationally unsafe to handle generically, or evals show generic output is misleading for a specific category and must be blocked or constrained. |
| MVP technology domain and specialists | `accepted` | Include `TechnologyDomainAnalystAgent` in MVP, with MVP specialists for monitors, smartphones, laptops, earphones/headphones, TVs, and smartwatches. Route technology products through the domain layer before specialist selection. | Adding the higher-level technology domain early is easier than retrofitting it after several direct specialists exist. The domain layer can own shared technology-product reasoning while specific specialists refine category details. | MVP scope must be reduced for delivery reasons, or evals show a specialist is too weak to ship and should fall back to technology-domain analysis until improved. |
| Reusable source-agent ownership | `accepted` | Keep reusable source intelligence agents outside the product/category hierarchy. They gather source-specific evidence and hand structured evidence back to product analysts and decision agents; they do not make final purchase recommendations. | YouTube reviews, marketplace availability, brand stores, professional reviews, and community signals can support multiple product categories. Treating them as reusable tools avoids duplicating source logic inside every specialist. | A future source capability becomes category-specific enough that it belongs inside a specialist, or a provider/compliance constraint requires narrower ownership. |
| YouTube review intelligence MVP status | `accepted` | Keep `YouTubeReviewIntelligenceAgent` as `candidate-mvp`, not `required-mvp`. Implement it only after the generic workflow and provider abstractions exist, and only if metadata/transcript provider constraints remain acceptable. | Video reviews can add high-value real-world evidence, but transcript access, reliability, quota, terms, and implementation cost should not block the core MVP. The capability remains reusable source intelligence, not a category specialist. | Project owner promotes video review evidence to required MVP scope, or early evals show video evidence is critical enough to promote to `required-mvp`. |
| YouTube transcript/provider strategy | `accepted` | Use official YouTube Data API metadata where configured. Do not assume transcript access. Use transcript text only through authorized official caption access, user-provided transcript input if later added, or an explicitly approved third-party transcript provider. Always represent transcript gaps. | Official metadata discovery is feasible, but official caption download is authorization-scoped and not a general public transcript API. Unofficial transcript providers carry reliability, quota, terms, and compliance risk. | A compliant transcript provider is approved, the project owner accepts a specific third-party provider risk, or the MVP deliberately chooses metadata-only video evidence. |
| Suspicious-listing treatment | `accepted` | Treat seller/listing legitimacy as a first-class analysis concern. Suspicious or weak listings must be surfaced, penalized, blocked, or clearly warned about separately from product quality. Deterministic suspicious flags must not be silently overridden by agent output. | CartCart exists partly to help users avoid bad or suspicious purchases. A good product from a risky seller should not become a safe recommendation. | Trust signals prove too sparse for a category/source, requiring an `unknown` trust state, or legal/product guidance changes how risk wording should be presented. |
| Raw snapshot retention | `pending` | Store structured source and evidence records in SQLite. Store bulky raw artifacts under `data/` only when useful for auditing, debugging, extraction replay, or evals. Define configurable retention/deletion rules before live provider use. | The plan favors local evidence retention for session continuity and evalability, but raw HTML, extracted text, screenshots, and traces can grow large and may contain sensitive content. | Storage/privacy concerns require shorter retention, provider terms restrict stored content, or eval/debug needs require explicit longer retention for selected fixtures. |
| Observability backend choice | `pending` | Use OpenTelemetry concepts from the start and keep exporters backend-neutral. Use Logfire as the default local/development backend if acceptable; otherwise use console/local OTEL export with structured JSON logs. | Logfire aligns with Pydantic, FastAPI, AI/LLM observability, and span-based evals. Exporter-neutral instrumentation avoids locking implementation to one backend. | Logfire is not acceptable for privacy/cost/account reasons, another OTEL backend is selected, or local-only console/file traces are preferred for MVP. |
| Future domain-layer timing | `accepted` | Add `TechnologyDomainAnalystAgent` now because multiple MVP technology specialists are approved. Keep other broad domain layers, such as kitchen appliances, postponed until they have multiple specialists or shared rules. | Higher-level domain agents are harder to add after direct specialist routing spreads. Adding the technology domain now preserves modularity while avoiding empty non-technology layers. | A future non-technology domain gains enough specialists or shared evaluation rules to justify a domain layer. |
| Tool-vs-handoff policy | `accepted` | Use typed steps, tools, or sub-runs for MVP agents. Do not use OpenAI Agents SDK handoffs as the normal control plane. Consider handoffs only when a specialist must take over a conversational turn. | CartCart needs persisted workflow state, retries, source evidence, evalability, and inspectable intermediate artifacts. Deterministic orchestration keeps those responsibilities explicit. | A future conversational workflow needs specialist ownership of a user turn and can still preserve persistence, traceability, and fallback behavior. |
